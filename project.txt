I checked the repo and here is the full project workflow, including the small steps that are easy to miss.

**Project Overview**
AgriConnect AI is an agriculture marketplace with:

- `backend`: FastAPI API, MongoDB, Redis, services, repositories, background jobs.
- `website`: Next.js web app for customer, farmer, delivery, warehouse, admin, business users.
- `mobile`: Flutter app with similar role-based flows.
- `ai`: AI/ML layer for demand, pricing, route, fraud, anomaly, and delivery-risk intelligence.
- `docker`: MongoDB, Redis, backend, website, Celery, Nginx, Prometheus, Grafana.
- `docs`: architecture and AI workflow documents.

Main backend entry: [backend/app/main.py](E:/agri/backend/app/main.py)

**System Start Workflow**
1. Developer starts the project using Docker or local commands.
2. MongoDB starts for permanent project data.
3. Redis starts for cache, OTP, sessions, revoked tokens, Celery broker/cache.
4. Backend FastAPI starts on port `8000`.
5. Backend connects to MongoDB.
6. Backend connects to Redis.
7. Backend seeds default product categories if none exist.
8. Backend creates audit-log TTL index.
9. Backend starts a reservation-expiry background loop.
10. Website starts on port `3000`.
11. Mobile app can call backend API directly.
12. Nginx can reverse-proxy website/backend in deployment.
13. Prometheus collects metrics.
14. Grafana displays monitoring dashboards.

**Backend Request Flow**
1. Request reaches FastAPI.
2. CORS middleware checks allowed origins.
3. Rate-limit middleware checks request limits.
4. Security-header middleware adds browser/security headers.
5. Exception handlers prepare consistent error responses.
6. Route handler receives request under `/api/v1/...`.
7. If protected, route calls `get_current_user`.
8. Token is decoded.
9. Token revocation is checked in Redis.
10. User is loaded from MongoDB.
11. User active/verified status is checked.
12. Route validates request schema.
13. Route calls service layer.
14. Service layer applies business logic.
15. Service calls repositories.
16. Repository reads/writes MongoDB.
17. Service may call Redis, notifications, payments, inventory, AI, or Celery.
18. Response is encoded, including MongoDB `ObjectId` conversion to string.
19. Client receives JSON response.

**Web App Request Flow**
1. User opens the Next.js website.
2. Page or component loads for the current route.
3. If data is needed, frontend calls `api.get/post/put/delete`.
4. API client gets current NextAuth session.
5. If session has an access token, it adds `Authorization: Bearer ...`.
6. Request goes to `/api/v1/...` on the Next.js app.
7. Next.js proxy reads the server session.
8. Proxy forwards the request to FastAPI at `http://localhost:8000/api/v1/...`.
9. Backend responds.
10. Proxy returns backend response to browser.
11. UI updates local state/store.
12. If backend returns `401`, frontend clears transient state, signs out, and redirects to login.

**Mobile App Request Flow**
1. Flutter app starts.
2. `ApiService.init()` loads saved auth token from shared preferences.
3. Mobile screen/provider calls `ApiService.get/post/put/delete`.
4. API service adds JSON headers.
5. If token exists, it adds `Authorization`.
6. Request goes directly to `http://localhost:8000/api/v1`.
7. Backend validates and responds.
8. Flutter provider updates state.
9. Screen redraws using the new data.
10. On logout, token is removed from shared preferences.

**Registration Workflow**
1. User opens register page.
2. User enters first name, last name, phone, email, password, confirm password, role.
3. Frontend checks password confirmation and required fields.
4. Frontend sends data to `/api/auth/register`.
5. Website auth route forwards to backend `/api/v1/auth/register`.
6. Backend checks whether email already exists.
7. Backend checks whether phone already exists.
8. If verified account exists, backend rejects registration.
9. If unverified account exists, backend sends a new OTP.
10. Backend validates password strength.
11. Backend creates user.
12. Password is hashed before storing.
13. Backend generates OTP.
14. OTP is hashed and saved in Redis.
15. OTP is sent through notification service.
16. In debug mode, OTP may be returned/logged for testing.
17. Frontend redirects user to verify page.
18. User enters OTP.
19. Backend verifies OTP hash.
20. Backend marks user verified.
21. Backend creates access token and refresh token.
22. User can now enter role dashboard.

**Login Workflow**
1. User opens login page.
2. User selects role.
3. User chooses email/password or phone OTP.
4. For password login, NextAuth sends credentials to backend `/auth/login`.
5. Backend authenticates email/phone and password.
6. If privileged role has TOTP enabled, backend requires authenticator code.
7. If user is not verified, backend sends OTP and blocks login.
8. Backend creates access token and refresh token.
9. Backend updates last login time.
10. Backend records session/device.
11. Backend writes audit log.
12. NextAuth stores JWT session.
13. User is redirected to `/{role}/dashboard`.
14. If selected role does not match backend role, login fails.

**OTP Login Workflow**
1. User enters phone number.
2. Frontend calls `/api/auth/login-otp`.
3. Backend normalizes phone number.
4. Backend checks registered user.
5. Backend generates OTP.
6. Backend stores hashed OTP in Redis with expiry.
7. Backend sends OTP.
8. User enters OTP.
9. Frontend calls `/api/auth/verify`.
10. Backend checks OTP exists.
11. Backend blocks after too many wrong attempts.
12. Backend verifies OTP hash.
13. Backend deletes OTP after success.
14. Backend creates tokens.
15. Frontend signs user into NextAuth using OTP provider.
16. User is redirected to correct role dashboard.

**Customer Workflow**
1. Customer registers/logs in.
2. Customer lands on customer dashboard.
3. Customer browses marketplace.
4. Customer searches/filter products.
5. Customer views product details.
6. Customer adds product to cart.
7. Cart store keeps selected items.
8. Customer manages quantity.
9. Customer may add wishlist items.
10. Customer selects delivery or pickup.
11. If delivery, customer selects saved address.
12. If pickup, customer selects pickup date/time.
13. Customer may apply coupon.
14. Customer proceeds to checkout.
15. Frontend creates order through `/orders`.
16. Backend validates customer role.
17. Backend validates address for delivery.
18. Backend validates pickup date for pickup.
19. Backend loads each product.
20. Backend checks inventory.
21. Backend prevents client-side price tampering.
22. Backend calculates subtotal.
23. Backend applies bulk price/discount if applicable.
24. Backend validates coupon.
25. Backend calculates delivery charge, platform fee, commission, discount, total.
26. Backend creates order in MongoDB.
27. Backend reserves/confirms inventory.
28. Backend decrements product quantity.
29. Backend creates payment intent.
30. Backend notifies farmer.
31. Customer sees order confirmation.
32. Customer can track order.
33. Customer can cancel if status allows.
34. Customer can confirm pickup for pickup orders.
35. Customer can review/rate after completion.

**Farmer Workflow**
1. Farmer registers/logs in.
2. Farmer opens farmer dashboard.
3. Farmer creates/updates profile and farm info.
4. Farmer creates product.
5. Product includes name, category, price, quantity, location, pickup options, bulk settings.
6. Backend stores product.
7. Inventory is tracked.
8. Customer places order for farmer product.
9. Farmer receives notification.
10. Farmer views incoming orders.
11. Farmer confirms pending order.
12. Farmer processes order.
13. Farmer marks order ready for delivery or ready for pickup.
14. If pickup, backend may generate pickup code.
15. If delivery, farmer can self-deliver or assign delivery partner.
16. Farmer can view delivery route groups.
17. Farmer can view analytics, earnings, customers, harvests, B2B RFQs, ratings.
18. Farmer may use AI demand/pricing/route insights.
19. Farmer completes order flow through delivered/picked-up status.
20. Farmer settlement/commission is handled through payment/ledger services.

**Order Status Workflow**
1. Order starts as `pending`.
2. Farmer/admin can move `pending` to `confirmed`.
3. Farmer/admin can move `confirmed` to `processing`.
4. Farmer/admin can move `processing` to `ready_for_delivery` or `ready_for_pickup`.
5. Delivery/admin/farmer can move `ready_for_delivery` toward dispatch/transit.
6. Delivery/admin can move `dispatched` to `in_transit`.
7. Delivery/admin can move `in_transit` to `delivered`.
8. Customer/farmer/admin can cancel only when rules allow.
9. Pickup order moves from `ready_for_pickup` to `picked_up`.
10. Delivered and picked-up are final states.
11. Cancelled is also final.
12. On cancellation, inventory is released.
13. On paid cancellation, refund processing can start.
14. On delivered/picked-up, payment status becomes paid.
15. Notifications are sent at important status changes.

**Delivery Workflow**
1. Delivery partner registers/logs in.
2. Delivery profile stores availability/location/performance.
3. Farmer marks order ready for delivery.
4. Farmer can request/assign delivery partner.
5. Backend can find nearest partner.
6. Partner receives assignment notification.
7. Partner accepts/works delivery.
8. Partner updates status to dispatched/in transit/delivered.
9. Partner location can be used for tracking.
10. Backend calculates remaining distance and ETA when coordinates exist.
11. Customer sees tracking data.
12. Delivery completion updates assignment, payment, inventory, and notifications.
13. Delivery ratings can be submitted.

**Warehouse Workflow**
1. Warehouse user logs in.
2. Warehouse dashboard shows stock/incoming/outgoing/transfers/cold storage.
3. Farmer products/orders may connect to preferred warehouse.
4. Incoming stock is recorded.
5. Stock is stored and updated.
6. Outgoing stock is processed for orders.
7. Transfers move stock between warehouses.
8. Cold-storage records manage temperature/storage-sensitive goods.
9. Warehouse analytics summarize stock movement.

**Admin Workflow**
1. Admin logs in.
2. Admin may require/enable 2FA.
3. Admin dashboard shows platform overview.
4. Admin manages users.
5. Admin manages farmers.
6. Admin reviews products.
7. Admin monitors orders.
8. Admin checks payments/finance/settlements.
9. Admin handles coupons.
10. Admin handles complaints.
11. Admin checks security/audit activity.
12. Admin views ratings.
13. Admin views AI insights.
14. Admin can filter all orders by user/status/date.
15. Admin can access broader operational reports.

**Payment Workflow**
1. Customer selects payment method: cash/card/UPI/wallet style options.
2. Backend creates order with `paymentStatus=pending`.
3. Backend creates payment intent through payment service.
4. If online payment succeeds, payment is marked paid.
5. If COD/pickup cash, payment may be finalized later.
6. Platform fee/commission is calculated.
7. For pickup cash, commission may be recorded against farmer settlement.
8. On cancellation after payment, refund processing starts.
9. Payment records and ledger/settlement services support finance screens.

**Inventory Workflow**
1. Farmer/product creation creates available stock.
2. Customer adds item to cart on frontend.
3. During order creation, backend checks available stock.
4. Backend reserves/confirms stock.
5. Product quantity is decremented.
6. Stock update can be broadcast.
7. If order is cancelled, inventory is refunded/released.
8. Background reservation expiry loop clears stale reservations.
9. Warehouse stock can track incoming/outgoing/transfers separately.

**Notification Workflow**
1. Events happen: OTP, registration, order created, status changed, delivery assigned, delivered, cancelled.
2. Service calls `NotificationService`.
3. Notification may be email, SMS, app notification, or internal notification.
4. Redis/cache/background tasks may support delivery.
5. User sees notification in website/mobile notification screens.

**AI Workflow**
1. Marketplace data is collected: users, orders, products, payments, inventory, delivery, GPS, ratings, cancellations, refunds.
2. Data is extracted from MongoDB.
3. Data is cleaned.
4. Features are engineered.
5. Training datasets are prepared.
6. ML models are trained separately from live production requests.
7. Models are stored in model registry.
8. Backend AI service loads/uses models.
9. AI APIs return predictions/recommendations.
10. AI does not directly ban users, change prices, cancel orders, or force actions.
11. Business rules and humans decide final action when needed.

AI features planned/documented:

- Fraud detection.
- Delivery-risk prediction.
- Demand prediction.
- Smart pricing.
- Community delivery optimization.
- Anomaly detection.
- Recommendations.

Main AI doc: [docs/AI_ARCHITECTURE.md](E:/agri/docs/AI_ARCHITECTURE.md)

**Data Storage Workflow**
1. MongoDB stores main business data.
2. Redis stores temporary/fast data.
3. Uploaded files are served from backend upload directory.
4. JWT tokens identify users.
5. Refresh tokens support session renewal.
6. Revoked token IDs are stored in Redis.
7. OTPs are stored as hashes, not raw OTP values.
8. Audit logs record security-sensitive actions.
9. Celery handles async/scheduled jobs.

**Testing Workflow**
1. Backend has pytest-style tests under `backend/tests`.
2. Backend also has specific OTP/Redis tests.
3. Website has Jest tests for utility/store logic.
4. Website has Cypress E2E tests for persistence/search behavior.
5. Tests should cover auth, orders, products, payments, delivery, security, KYC, admin, AI, warehouse, notifications.

**Deployment Workflow**
1. `.env` provides secrets and service URLs.
2. Docker Compose builds backend, website, mobile dev container, Celery, Redis, MongoDB, Nginx, Prometheus, Grafana.
3. Backend exposes `8000`.
4. Website exposes `3000`.
5. Nginx exposes `80` and `443`.
6. Prometheus exposes `9090`.
7. Grafana exposes `3001`.
8. Production compose uses production Dockerfiles/config.
9. Monitoring observes service health and metrics.
10. `/health` checks backend database and Redis health.

That is the full project flow as the repo currently shows it. One small but important note: the backend order domain logic is mostly in `services` and `repositories`; [backend/app/models/order.py](E:/agri/backend/app/models/order.py) is still a TODO stub.
